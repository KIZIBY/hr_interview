# OPERATIONS_GUIDE.md — эксплуатация: инциденты, runbook'и, откат

Status: ДЕЙСТВУЮЩИЙ (v1.0, 2026-07-02). Класс: **seed-док** (копия при bootstrap, дальше слой
адаптации; улучшения — upstream). Закрывает operation-фазу жизненного цикла: наблюдаемость ловит
ошибку (устав, инвариант observability/I-16-класса), этот док определяет, что происходит дальше.
On-call = владелец; агенты диагностируют, чинят по процессу и эскалируют — не «дежурят» молча.

---

## 1. Incident response — единый цикл

1. **Детект.** Источник: alert наблюдаемости / всплеск error-группы / жалоба. Всё user-facing
   обязано долетать до ingest с request_id (устав + `NFR_GUIDE.md` §2 Observability) — «пользователь
   заметил раньше системы» само по себе инцидент процесса, фиксируется как learning.
2. **Триаж.** Severity по шкале bug-handling: **P0** — прод лежит/данные под угрозой (немедленно,
   будим владельца), **P1** — ключевой флоу сломан (в работу сразу), **P2/P3** — по расписанию
   Kulibin. Тикет заводится ДО фикса (`docs/bug-handling-process.md` §1, dedup обязателен).
3. **Mitigate ≠ fix.** Сначала остановить ущерб: откат деплоя (§3), выключение опциональной
   подсистемы (graceful degradation), rate-limit. Mitigation помечается `// TEMP: … см. #тикет` —
   заплатка без тикета запрещена (I-11-класс).
4. **Root cause.** После стабилизации — ОБЯЗАТЕЛЬНЫЙ systematic-debugging до доказанной
   первопричины + scope-the-class (`bug-handling-process.md` §2/§4). Инцидент без root cause
   не закрывается.
5. **Post-mortem (для P0/P1).** Короткий разбор в `docs/audit-evidence/<дата>-incident-<slug>.md`:
   таймлайн (детект→mitigate→fix), первопричина, «почему не поймали раньше» (дыра наблюдаемости? →
   чинится как отдельный тикет), правила → `docs/pipeline-rules.md` / устав через владельца.
   Без поиска виноватых — ищем дыру в процессе.

## 2. Runbook-конвенция

- Путь: `docs/runbooks/<service|подсистема>.md`. Обязателен для каждого сервиса/критичной
  подсистемы; создаётся ВМЕСТЕ с сервисом (stage-4 Technical Writer проверяет), не «потом».
- Минимум разделов: **Как понять, что сломалось** (health, дашборд, типовые сигнатуры ошибок) ·
  **Как перезапустить безопасно** (команды, порядок, что НЕ трогать) · **Известные грабли**
  (инциденты с датами и ссылками на тикеты) · **Зависимости** (что тянет за собой).
- Runbook — живой: после каждого инцидента дополняется (та же дисциплина, что память агентов:
  append, не переписывание истории).

## 3. Откат (rollback)

- Деплой-скрипт проекта обязан уметь откат на предыдущую версию кода; команда отката — в runbook.
- Миграции: expand-then-deploy (сначала совместимая миграция, потом код); у каждой миграции есть
  Down-план ИЛИ явное «необратима + бэкап до» (pg_dump/аналог). Откат кода без отката данных —
  штатный путь; откат данных — только владелец.
- После любого отката — verify как после деплоя (health + smoke) + тикет на первопричину:
  откат это mitigation, не решение.

## 4. Роли

| Кто | В инциденте |
|---|---|
| Владелец | on-call, решения P0 (откат данных, downtime, коммуникация) |
| Kulibin | диагностика + фикс по bug-handling; runbook-обновление после фикса |
| Browser-QA (renata/her) | verify фикса на live с evidence (zero-trust: «FIXED» без проверки не существует) |
| Pushkin | post-mortem дока, актуальность runbook'ов (docs-freshness) |

Эскалация всегда явная: тикет + `NEEDS_ORACLE`/упоминание владельца — «понадеялся, что заметит» = потерянный инцидент.

## 5. Метрики: DORA и контракт автономии

**Рабочая панель** — Flight Deck: `bash scripts/pipeline-dashboard.sh` → `docs/pipeline-dashboard.html`
(DORA-блок сверху + trace прогонов). Терминальный срез: `bash scripts/dora-metrics.sh [--days N]`.
Источники — только живые файлы репозитория: git-история, `specs/*/audit.md`, `docs/ops-journal.md`.

| Метрика | Как считается | Кто обязан кормить |
|---|---|---|
| Deployment Frequency | `deploy:done` в ops-journal за окно | деплой-скрипт проекта в конце зовёт `bash scripts/ops-log.sh deploy:done "<sha>"` (fail-ветка — `deploy:failed`) |
| Lead Time | медиана `init` → `quality-verdict PASS` по audit.md прогонов | state-машина пишет сама |
| Change Failure Rate | (`deploy:failed` + `incident:open`) / `deploy:done` | ops-log из §1 и деплой-скрипта |
| MTTR | медиана `incident:open <slug>` → `incident:resolved <slug>` | триаж (§1): open при детекте, resolved после root-cause фикса |
| **Автономия** | агентные коммиты (`Co-Authored-By`) / все коммиты за окно | конвенция коммитов уже обязывает маркер — метрика самособирается |

**Контракт автономии:** цель — **≥40% изменений в автономном цикле** (порог: env `AUTONOMY_TARGET`,
по умолчанию 40). Панель красит метрику красным ниже цели. Метрика честная и грубая (по маркеру
коммитов); дополнительный срез — гейты владельца (approved/revise) из audit.md: много revise =
автономия «формальная». Ниже цели → причина разбирается как learning (что блокирует агентов),
НЕ накруткой коммитов (zero-trust применим и к своим метрикам).
