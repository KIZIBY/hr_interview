# NFR_GUIDE.md — нефункциональные требования: квантификация обязательна

Status: ДЕЙСТВУЮЩИЙ (v1.0, 2026-07-02). Класс: **seed-док** (копируется при bootstrap, далее — слой
адаптации; улучшения — upstream в mothership). Где работает: секция `## Non-Functional Requirements`
в spec.md, аудит `/pipeline-stage2`, эвристика `scripts/spec-lint.sh`.
Security-категория вынесена в отдельную доктрину: `Product_agents/SSO_AUTH_GUIDE.md`
(секция `## Authentication & Access` в спеке — обязательная, отдельная от NFR).

## 1. Правило: NFR без числа не существует

Формулировки **«быстро», «надёжно», «безопасно», «масштабируемо», «удобно», «отзывчиво»,
«как сейчас, только лучше» — запрещены** как финальный текст требования. Это заготовки вопросов,
не требования: их нельзя проверить в stage-4, значит нельзя и «выполнить».

Каждый NFR фиксируется в форме:

```
NFR-XXX (категория): метрика — целевое значение — метод измерения — условия (объём/нагрузка)
```

Пример: `NFR-003 (performance): p95 ответа GET /api/v1/meetings — ≤300 мс — k6 smoke на стейдже — при 50 одновременных пользователях и 10k совещаний в БД`.

Если категория к фиче не применима — **явное `N/A (<категория>: почему)`**, не молчание
(правило честного coverage, как в `Authentication & Access`).

## 2. Пять категорий (чек-лист на каждую фичу)

| Категория | Что квантифицировать | Vague → квантифицированный (пример) |
|---|---|---|
| **Performance** | latency (p50/p95), throughput, время фоновых задач, ресурсы | «экспорт быстрый» → «экспорт PDF ≤5 с при протоколе 50 стр (p95, стейдж)» |
| **Scalability** | объём данных, конкурентность, темп роста | «выдерживает нагрузку» → «500 concurrent WS-сессий; список стабилен при 10k строк (keyset)» |
| **Reliability** | доступность, деградация, восстановление, целостность | «надёжно» → «отказ AI-подсистемы не блокирует CRUD (graceful degradation); RPO=0 по данным совещаний» |
| **Observability** | перехват ошибок, корреляция, retention, алёрты | «есть логи» → «user-facing ошибки фичи долетают до ingest с request_id; ретеншн ≥7д; alert на всплеск» |
| **Security** | → отдельная секция `## Authentication & Access` (`SSO_AUTH_GUIDE.md` §3) + аудит мутаций, защита данных | «безопасно» → «RBAC на каждом endpoint фичи; мутации в audit-log; секреты в env» |

Ориентиры целей — **инварианты устава проекта** (в reference-уставе X5: graceful degradation I-8,
observability I-9, data-integrity I-15, traceability/coverage I-16): NFR фичи конкретизирует
инвариант числом, а не переизобретает планку.

## 3. Где живёт в пайплайне

- **spec.md (`## Non-Functional Requirements`)**: NFR по категориям §2, каждый в форме §1;
  неприменимые категории — явное N/A. Базовая линия: если цель «не хуже текущего» — сначала
  ЗАМЕРЬ текущее (число в спеку), «как сейчас» без замера — vague.
- **stage-1 (Creative)**: Creative Director собирает NFR по этому гайду; **Hard Critic обязан
  оспорить завышенные цели** — enterprise-планки для внутреннего инструмента на 400 совещаний/год
  это over-engineering (YAGNI), заниженные для критичного пути — риск.
- **stage-2 (Audit)**: ревьюеры проверяют каждый NFR на форму §1; неквантифицированный NFR =
  **WARNING** (CRITICAL, если фича затрагивает производительность/надёжность напрямую);
  вопросы «сколько именно?» → возврат на stage-1/clarify, не догадка аудитора.
- **spec-lint.sh**: NFR-секция без единого числа → `warn` (эвристика-сигнал, не гейт —
  принцип «hard-гейты ≠ coverage-цели», `ADAPTATION_PIPELINE.md` §1.4).
- **stage-4 (Quality)**: каждый NFR проверяем как требование — замер по заявленному методу
  или явный перенос с решением владельца; NFR без способа проверки не должен был пройти stage-2.

## 4. Анти-паттерны

1. **Цель без метода**: «≤300 мс» без «чем и где мерим» — не проверить → не NFR.
2. **«Как сейчас» без базовой линии**: сначала замер текущего, потом цель.
3. **Enterprise-цирк для внутренней тулзы**: 99.99% availability там, где владелец согласен на
   «починим утром» — Hard Critic режет (YAGNI).
4. **NFR-косплей функционалки**: «система должна отправлять email» — это FR, не NFR.
5. **Молчаливое N/A**: пропущенная категория читается как «не подумали», а не «не применимо».
6. **Двухбэкендная фича без матрицы** (урок spec 005 mothership, 2026-07-03): фича с ≥2
   бэкендами/провайдерами (tracker|github, СУБД×2, …) формулирует NFR и тесты построчной
   матрицей возможностей (бэкенд × сценарий × деградация), а не «в среднем работает на обоих» —
   асимметрии бэкендов это требования; непокрытые пересечения (fail первого → фолбэк →
   fail проверки второго) прячутся именно в «среднем».
