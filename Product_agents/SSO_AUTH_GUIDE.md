# SSO_AUTH_GUIDE.md — корпоративная аутентификация продукта ({{SSO_PROVIDER}})

Status: ДЕЙСТВУЮЩИЙ (v1.0, 2026-07-02). Класс: **seed-док** (копируется при bootstrap, далее — слой
адаптации; улучшения направлять upstream в mothership). Механика подключения: `ADAPTATION_PIPELINE.md` §11.
Параметры: `SSO_PROVIDER` / `SSO_ISSUER_URL` / `SSO_ADMIN_GROUP` в `team.params` (§4 пайплайна).

**Для продуктов X5 стандарт — «X5 Ключ»** (корпоративный SSO X5 Group: OAuth 2.0 / OpenID Connect,
Keycloak). Большинство наших продуктов разрабатывается для X5 → анкета нового проекта по умолчанию
рассматривает `SSO_PROVIDER="X5 Ключ"`. `SSO_PROVIDER="-"` = у проекта нет корпоративного SSO —
этот док спит (но секция «Authentication & Access» в спеках всё равно обязательна, см. §3).

---

## 1. Правило по умолчанию

**Если у продукта есть пользовательский вход — вход идёт через корпоративный SSO {{SSO_PROVIDER}},
а не через самодельный логин/пароль.** Роли и права управляются централизованно (AD/LDAP-группы →
роли продукта), 2FA и политика паролей наследуются от SSO. Исключение (локальная аутентификация,
демо-режим, публичный продукт без корпоративных пользователей) — только явным решением владельца,
зафиксированным в спеке (`## Authentication & Access` + `## Assumptions`).

Fallback-правило: локальная аутентификация при недоступности SSO-провайдера — только для УЖЕ
провиженных пользователей, НЕ безусловный auto-provision любого входящего.

## 2. При старте (bootstrap / онбординг проекта)

1. **Анкета (шаг 0):** заполни `SSO_PROVIDER`, `SSO_ISSUER_URL`, `SSO_ADMIN_GROUP` в `team.params`.
2. **Bootstrap (шаг 1):** `agent-team-adapt.sh` копирует этот док и штампует секцию
   `AUTH STANDARD` в `AGENTS.md` — агенты видят стандарт с первого прогона.
3. **Онбординг (шаг 1.5a):** Onboarding Report обязан зафиксировать **текущий механизм
   аутентификации** (провайдер, где живёт auth-код, откуда берутся роли, как логинятся тест-юзеры).
4. **Регистрация приложения** (если интеграции ещё нет) — через IT Service Desk / команду ИБ
   заказчика. Для X5 Ключ заявка содержит:

| Параметр | Значение |
|---|---|
| Название приложения | `HR Interview FDE` |
| Redirect URI | `http://localhost:8000/auth/callback` (+ dev-URI отдельной строкой) |
| Logout URI | `http://localhost:8000/` |
| Scope | `openid profile email groups` |
| Тип клиента | по решению ИБ: confidential (server-side, client_secret) ИЛИ public + PKCE S256 |

   Получаешь: `CLIENT_ID`, `CLIENT_SECRET` (только для confidential), issuer `{{SSO_ISSUER_URL}}`,
   документацию API. Названия групп каталога для ролей согласуются там же (пример маппинга:
   `{{SSO_ADMIN_GROUP}}` → `admin`, группа «все сотрудники» → `user`).

## 3. При работе с требованиями (BLOCKING для spec-этапов)

Каждая спека фичи, затрагивающей **вход, пользователей, роли или доступ**, обязана содержать
секцию `## Authentication & Access` (шаблоны: `speckit.specify`, `/pipeline-stage1`; проверка:
Security Reviewer + Constitution Gate в `/pipeline-stage2`). Минимум секции:

- **Способ входа:** SSO {{SSO_PROVIDER}} (по умолчанию) / исключение с обоснованием и решением владельца.
- **Источник ролей:** группы каталога → маппинг на роли продукта (таблица; `{{SSO_ADMIN_GROUP}}` → admin).
- **Сессии:** logout (локальный + SSO-logout), истечение/refresh, ревокация при деактивации в каталоге.
- **Тест-доступ для QA:** тест-учётки (`TEST_USERS_DOC`) и/или тест-байпас — как QA-агенты входят (§5).
- **NFR-ссылка:** инварианты §4 применимы — отметить затронутые.

Фича не затрагивает вход/доступ → секция из одной строки «N/A (не затрагивает вход/роли/доступ)» —
явное «нет» вместо молчания (правило честного coverage).

## 4. Инварианты реализации (проверяет stage-2 аудит и code-review)

1. **Flow:** OAuth 2.0 Authorization Code (+ **PKCE S256** для public client; X5 Ключ в
   public-режиме client_secret НЕ отправляется и НЕ логируется).
2. **CSRF/replay:** `state` обязателен (httpOnly-cookie), `nonce` + audience-verify для ID-токена.
3. **Секреты** (`SSO_CLIENT_SECRET`, `SESSION_SECRET`): только env/secret-store, вне репо; никогда
   в коде, логах, argv, тикетах, скриншотах. Ротация — по регламенту ИБ заказчика.
4. **Токены не в localStorage/sessionStorage.** Сессия — на бэкенде, cookie `httpOnly` (+ `secure`
   в проде); фронтенд получает пользователя через `/auth/user`, не хранит токены сам.
5. **HTTPS обязателен в проде;** redirect URI — точное совпадение с регистрацией, без wildcard.
6. **Роли только из каталога:** маппинг групп → роли на бэкенде; никаких self-claimed ролей из
   фронтенда. Деактивация пользователя в каталоге → ревокация активных сессий/refresh-токенов,
   не только запрет нового входа.
7. **Наблюдаемость auth-событий:** failed login, token refresh, group-sync — логируются с
   request_id (совместимо с инвариантом наблюдаемости устава проекта).
8. **Egress-дисциплина интеграций** (урок spec 005 SEC-1, 2026-07-03): каждая интеграция,
   отправляющая данные наружу (тикеты, вебхуки, внешние API), явно объявляет в спеке — ЧТО
   покидает периметр, КУДА и при каких условиях; свободный текст владельца/пользователя во
   внешнюю систему — только после проверки видимости приёмника (публичный репозиторий/канал →
   явный confirm, не молчаливый дефолт).

Env-конвенция (имена подставь под проект; в X5-проектах исторически префикс `X5_KEY_*`):
`SSO_CLIENT_ID`, `SSO_CLIENT_SECRET`, `SSO_ISSUER_URL={{SSO_ISSUER_URL}}`,
`SSO_CALLBACK_URL=http://localhost:8000/auth/callback`, `SESSION_SECRET` (случайная строка 32+).

## 5. QA-слой (browser-QA: renata / semiglazka / her / zemlemer; e2e: zanuda)

- **Вход — через видимую SSO-форму** (правило visible-browser evidence сохраняется) ЛИБО через
  документированный **тест-байпас** (тест-login route / тест-realm): байпас обязан быть выключен
  в prod-конфиге или ограничен доменом тест-пользователей `{{TEST_EMAIL_DOMAIN}}`. Наличие и
  способ байпаса фиксируются в `AGENTS.md` секции AUTH STANDARD при локализации (шаг 2).
- **Rate-limit дисциплина:** не дёргать SSO login-API напрямую в цикле — фикстуры/storageState
  (паттерн zanuda: токены обновляет только global-setup, не тесты).
- **Секрет-дисциплина:** пароли тест-юзеров, cookies, auth-заголовки не публикуются в
  issues/скриншотах/памяти (общее правило `AGENTS.md`).
- **RBAC-проверки:** enforcement-probe обеих сторон — «кнопка спрятана ≠ endpoint запрещён» и
  «кнопка видна ≠ действие разрешено»; для SSO-ролей — смена группы в каталоге должна менять
  права после re-login (проверка маппинга, не UI).

## 7. Рекомендуемый инвариант для устава целевого проекта

Целевой проект пишет свой `docs/constitution.md`; при наличии корпоративного SSO рекомендуем
включить инвариант (номер — свой):

> **I-x. Enterprise Auth Governance (MUST).** Вход — через корпоративный SSO ({{SSO_PROVIDER}});
> роли — только из групп каталога; секреты SSO — вне репо; токены — не в web-storage;
> state+nonce+PKCE — обязательны; деактивация в каталоге ревоцирует сессии; auth-события
> наблюдаемы (request_id). _Как проверить:_ спека содержит «Authentication & Access»; дифф
> auth-кода проходит инварианты `SSO_AUTH_GUIDE.md` §4. _Канон:_ `Product_agents/SSO_AUTH_GUIDE.md`.
