## 0. Почему планка enterprise

HRI обрабатывает данные, потеря или искажение которых недопустимы (доменную специфику — какие именно данные и почему критичны — впиши на Шаге 2 локализации; reference-пример X5: юридически значимые governance-данные — заседания, голосования, протоколы, ЭЦП). **Данные sacred — их нельзя терять или искажать.**

Отсюда базовый принцип всего процесса:

> **Заплатка на симптом — запрещена. Каждый баг лечится в корне, системно и долговечно.**

## 1. Intake — баг пришёл от владельца в чат

> Тикет-бэкенд — по `team.params` (`ISSUE_BACKEND`): `tracker` → находки в корпоративном трекере по протоколу `Product_agents/Dev_Agents/XTRACKER_FILING.md` (`xt` CLI, префикс `[<Имя>]`; GitHub — фолбэк при недоступности трекера, если настроен реконсайлер); `github` → `gh issue`. Коммент/закрытие — в том трекере, где тикет заведён. (Reference X5: переходный период GitHub→XTracker с 2026-06-25, sync держит Пристав-реконсайлер.)

Запускается **немедленно**, одним непрерывным циклом, без gate'ов на одобрение между фазами:

1. **Сразу** завести GitHub issue с полной структурой: `## Контекст` (дата + дословная цитата) · `## Симптомы` · `## Возможные причины` · `## Желаемое поведение` (чек-лист приёмки) · `## Severity` (дефолт **P0/P1** для прямого фидбэка владельца) · `## Связанные`.
2. В том же цикле диспатчить fix-пак на investigate + fix — **приоритет ВЫШЕ backlog P1–P3**.
3. **Renata verify-gate** после деплоя (multi-surface, multi-state, реальный браузер).
4. Закрывать **только** со скриншот-evidence.

**Железное правило:** каждый фидбэк владельца доводится в одном цикле, не откладывается на approval-gate.
Эталон: `#1992` → Pack 69 (preflight-модалка) → Renata #45 verify.

## 2. ОБЯЗАТЕЛЬНО — `superpowers:systematic-debugging` на ЛЮБОЙ баг

При **любом** найденном дефекте, при **любой** критичности (P0 / P1 / P2 / P3) — прежде чем предлагать или писать фикс — прогнать через skill **`superpowers:systematic-debugging`**.

- Никаких «и так понятно» / «сразу в код». **Тривиальность симптома ≠ тривиальность причины.**
- Порядок: **воспроизвести → изолировать → найти root cause → доказать гипотезу (тест / лог / repro) → только потом фикс.**
- Это касается и однострочных опечаток: систематическая отладка подтверждает, что однострочник и есть настоящая причина, а не маскировка более глубокого дефекта.
- **Фикс без доказанного root cause = не фикс. Не закрывать.**

Это правило безусловное: оно не отменяется ни срочностью, ни «очевидностью», ни низкой критичностью.

## 3. Enterprise-решение, а не заплатка

- Лечи **причину**, а не симптом.
- Выбирай **архитектурно правильное и долговечное** решение, даже если оно дороже быстрого workaround.
- Workaround допустим **только** как явно помеченный временный (`// TEMP: <причина>, см. #<issue>`) со ссылкой на тикет системного фикса. **Молчаливая заплатка — нарушение.**
- Антипаттерн «comment-as-promise» (комментарий «сервис X гарантирует Y» без реального вызова) — запрещён (корень #2832).
- Если правильное решение крупное — заведи issue/спеку на системный фикс и доведи через speckit; не оставляй симптоматическую правку как финал.

## 4. Scope-the-class — бери весь класс в скоуп

Для каждого бага **обязательный вопрос:** «Может ли это повторяться в других частях системы?»

Если да:

- Найди **ВСЕ** вхождения паттерна (`lvdcp_pack` / grep / audit), а не только репортнутое место.
- Почини **КАЖДУЮ** ось: роль, membership-axis, состояние, поверхность (list / detail / export / sidebar / notification). Один фикс по одной оси, когда осей четыре, — это ~15% покрытия (урок #3074: 4 office-blind gate-класса, первый фикс закрыл ~15%).
- Поставь **guard против регрессии:** тест, CI-lint, структурный barrier (пример — #2872 structural CI guard против mobile-overflow).
- Регистрируй как **defect-family** и веди до полного закрытия класса, а не одного симптома.

| List fixed → detail forgotten | #2825 → #2832 → #2847 → #2848 |

## 5. Три сквозных стража каждого фикса: архитектура / производительность / безопасность

Любой фикс обязан **не ухудшать** (а по возможности — улучшать) систему по трём осям. Проверять **до** закрытия:

### Архитектура
- Clean architecture: handler → service → repository, без дублирования логики.
- Предикаты доступа/фильтрации — **внутри единого пагинированного SQL сервиса**, не post-hoc в api-gateway (append → cross-page дубли; filter → пустые страницы).
- `loadXForCaller`-дисциплина для любой multi-tenant таблицы (`WHERE id=$1 AND company_id=$caller`, 404-oracle).
- Frozen-контракты (JWT shape, NATS subjects append-only) не сломаны.

### Производительность
- Нет N+1, есть keyset-пагинация и нужные индексы.
- Нет лишних запросов/перерисовок; рост объёма данных не растит latency.
- Тяжёлые операции — батч / `FOR UPDATE SKIP LOCKED` / фон (Temporal), не в hot-path.

### Безопасность
- RBAC-резолвер прав и enforcement (`checkPerm`) **синхронны** (право видно в UI ⇒ действие не должно отдавать 403; корень #3004).
- RLS **fail-closed**, не fail-open (явный `company_id`, не COALESCE-идиом под superuser; находка F-02).
- Tenant-isolation: cross-tenant → **404-oracle**, не 403; denied read + denied mutation + owner-state unchanged.
- Default-deny: grant-строки пишутся в create-tx, не лечатся read-guard'ом (корень #2911).
- Нет утечки секретов/PII/токенов/cookie в логи, issue, скриншоты, память.

## 6. Никому не верь на слово — всё перепроверяй сам (evidence-first, zero-trust)

**Все врут** — репортёр бага, агент-разработчик и его «готово / FIXED / протестировал», зелёный CI, чужой verdict, и даже твои собственные прошлые выводы и память. Это не про злой умысел — про ошибки, оптимизм, устаревший контекст и confirmation bias. Доверие = дефект процесса.

- **Любое утверждение о результате** (фикс работает, тест прошёл, баг закрыт, «я проверил») принимается ТОЛЬКО с воспроизводимым доказательством, которое **ты получил и осмотрел сам**: свежий repro, прогон теста с выводом в логе, UI-раунд-трип в реальном браузере с hard-reload, запись в БД через `psql`, live bundle diff. Нет evidence — claim не существует.
- **Скепсис к агенту-разработчику особенно:** «FIXED» без свежей ревалидации на безопасных/disposable данных — не доверять. Background-агенты «зависают» с нулём коммитов, но рапортуют прогресс — проверяй git landing (`git log origin/main`), не слова.
- **Скепсис к себе:** память — point-in-time, устаревает; верь живому коду/состоянию, не воспоминанию. «Verified» прошлого фикса ≠ симптом ушёл (#3141 — у logout-15м было ДВА совпадающих root cause; первый «verified» симптом не закрыл).
- **Изолированный PASS ≠ сквозной PASS:** curl-200 не доказывает UI-флоу; stub-querier тест не доказывает SQL под body-ролью; «пусто / не приходит» — проверь РЕАЛЬНУЮ запись в БД, не фронт (так вскрылся 2-недельный audit-outage #2999).
- **Перепроверяй на другой оси, чем источник claim'а:** разработчик «проверил curl'ом» → ты проверяешь браузером; «прошло на admin» → ты гоняешь под non-admin; «починил на десктопе» → проверь 375px.

## 7. Fix → test → deploy → verify → close (общий loop)

1. **Diagnose** — §2 (systematic-debugging), доказанный root cause.
2. **Decide** — trivial (single-file < 50 LoC) vs speckit (multi-file / API / migration / cross-service); ambiguous → `superpowers:brainstorming` до спеки. Всегда §3 (enterprise) + §4 (scope-the-class).
3. **Test** — frontend `tsc --noEmit` 0 new errors + vitest; backend `go test ./...`; build затронутых сервисов; e2e smoke. Для не-admin изменений — реальный DB-запрос под body-ролью (stub-querier + platform_admin smoke пропускают SQL/schema-мисматчи).
4. **Deploy** — `./scripts/deploy.sh` (10 safety-checks, никогда не перезаписывает `.env`); миграции применяются отдельно через psql.
5. **Verify** — Renata в реальном браузере: кнопка там, где ждёт юзер; клик без console-ошибок и 4xx/5xx; результат виден после hard-reload; соседние экраны не регрессировали. **UI показывает Y, а backend отдаёт X = P0 data-loss, не «backend работает».**
6. **Close** — только с published SHA + deploy + test + screenshot-evidence. Дубликат / defer / `NEEDS_ORACLE` проговаривается явно с маршрутом, не описывается как fixed.

## 8. Definition of Done (self-audit перед закрытием тикета — XTracker `xt issue close <KEY>` или GitHub `gh issue close` при фолбэке; см. `Product_agents/Dev_Agents/XTRACKER_FILING.md`)

Закрывать **только** если на все ответы «да»:

1. Root cause доказан через `superpowers:systematic-debugging` (§2)?
2. Решение системное/долговечное, не заплатка; workaround (если есть) помечен и тикетирован (§3)?
3. Проверено, повторяется ли класс в других местах; весь класс в скоупе; поставлен guard от регрессии (§4)?
4. Архитектура / производительность / безопасность — не ухудшены, проверены (§5)?
5. Claim «готово/FIXED» (агента, репортёра, CI, своей памяти) перепроверен СОБСТВЕННЫМ свежим evidence, желательно на другой оси (§6)?
6. Tests: frontend tsc 0 new errors, backend `go test` PASS, smoke PASS?
7. Non-admin путь проверен реальным DB-запросом под body-ролью (если применимо)?
8. Deploy `./scripts/deploy.sh` → exit 0 + «DEPLOY SUCCESSFUL»?
9. Renata UI-verify на live — PASS, со скриншотом?
10. Cross-place consistency (list ↔ detail ↔ export ↔ sidebar) — без расхождений?
11. **Наблюдаемость (I-16):** для нового/изменённого user-facing-функционала — ошибочные пути перехватываются на каждой поверхности и долетают до ingest (не в 404-void); клиентская ошибка несёт `request_id`, совпадающий с серверным логом; ошибки фичи ищутся в error-store за ≥7д; есть alert/triage-путь на новую/всплесковую группу?

Если хоть один «нет» → **не закрывать.** Reopen / blocker-comment / лог в память.
